Dataset audit

Both files were identified by content, not filename — there were no “(2)” version-suffix duplicates to disambiguate; the folder contains exactly one players file and one match-performance file.

players.xlsx 56 rows × 8 columns

player_id, player_name, date_of_birth, primary_role, batting_style, bowling_style, academy_join_date, player_status

  • 56 unique player_id values, zero duplicates.
  • primary_role: Batter 20 · Bowler 18 · All-Rounder 12 · Wicketkeeper-Batter 6 — already using the exact required role vocabulary.
  • player_status: Active 44 · Inactive 8 · Left Academy 4 (three states, not the strict binary the brief assumes — see Section I).
  • Zero missing values in any column.
  • date_of_birth spans 2006-07-22 to 2009-03-04; academy_join_date spans 2019-11-22 to 2023-05-12.
  • As of today's date, 20 of 56 players compute to over 19 years old — expected, since match history runs through 2025 and players age out of U19 over time; eligibility must be checked against the relevant season, not the current date.
match_performance.xlsx 2,750 rows × 25 columns

match_performance_id, match_id, player_id, match_date, opponent, venue, match_result, did_bat, batting_position, runs, balls_faced, fours, sixes, is_out, did_bowl, balls_bowled, runs_conceded, wickets, dot_balls, maidens, wides, no_balls, catches, run_outs, stumpings

  • 2,750 unique match_performance_id values across 250 unique matches and all 56 players — zero duplicate (player_id, match_id) combinations.
  • Every player_id in this file exists in players.xlsx and vice-versa — clean referential integrity, no orphans either direction.
  • Match metadata (date, opponent, venue, result) is internally consistent for every match_id — zero matches with conflicting metadata across their player rows.
  • match_date spans 2023-06-01 to 2025-05-24 (3 seasons); match_result: Loss 1,232 · Win 1,144 · No Result 242 · Tie 132.
  • Batting fields are null exactly when did_bat = 0 (764 rows); bowling fields are null exactly when did_bowl = 0 (1,200 rows) — missingness is structural, not a data quality issue.
  • Cricket-validity checks all pass: no negative runs/wickets/balls, 4×fours + 6×sixes never exceeds runs, balls_bowled capped at 24 (the T20 4-over limit), wickets per innings capped at 5, economy rates range 2.5–16.3 (realistic), zero batting-position collisions between two of the academy's own players in the same match.
  • Domain consistency: stumpings occur only for Wicketkeeper-Batter players (75 of 75); average batting position by role is realistic (WK ~1.1, Batter ~3.4, All-Rounder ~6.3, Bowler ~8.8).
  • No pre-existing “performance score” or similar target column — nothing to audit for inherited target leakage; the ML target will be defined from scratch in Phase 11.
  • Matches per player range 41–57 (mean 49) across 3 seasons — enough history per player for chronological train/test splitting and rolling recent-form features.
  • No training/attendance/fitness/coach-rating data of any kind is present in either file — confirms the Section 58 gap: a synthetic Training_Records dataset must be generated before FR4 or the full feature set can be built.

Overall read: this is an unusually clean pair of datasets — zero missing values where values are expected, zero duplicate keys, zero impossible cricket statistics, and role-consistent domain patterns (stumpings only for wicketkeepers, batting order sensible by role). That level of cleanliness is realistic for carefully prepared sample data but not typical of raw manual academy records, so it will be treated and disclosed as SYNTHETIC PROTOTYPE DATA unless you confirm it is genuine academy history — this affects only the labelling in the final report, not how it's used.

Proposal vs. current system mismatches

Everything found while comparing the proposal, the four prototypes and the two datasets, sorted by what it means for the build.

Required fix
!Admin has no general User Management view

Admin Management only lists administrator accounts (username, phone shown for coaches elsewhere). FR1/FR17 need a broader User Management view covering Admin+Coach+Player login accounts, status and role.

Resolution Add a User Management page in Phase 6, alongside the existing Admin Management page. Admin Management can remain focused on administrator accounts; User Management becomes the FR1/FR17 canonical account-status view. Creating a Coach or Player still auto-creates the linked Users row underneath.

!Coach “Performance Entry” combines Match + Training into one form

Section 26/28 of the brief require distinct Match Entry and Training Entry pages/functions; the current prototype's single form mixes batting/bowling/fielding fields with drills/fitness/coach-rating fields.

Resolution During React conversion (Phase 7), split the existing field groups into two pages: “Batting/Bowling/Fielding” → Match Entry, “Training, Drills & Evaluation” → Training Entry. All field names, scales (Coach Rating 1–10, Fitness 0–100) and validation logic already in the prototype are reused as-is.

!Login page shows unsupported live statistics

“24 Athletes Tracked / 88/100 Avg AI Score / 92% Prediction Accuracy” are hardcoded numbers with no backing system yet, and “Prediction Accuracy” is not a valid metric name for a regression model.

Resolution Compute “Athletes Tracked” from a real (public, non-sensitive) player count once the backend exists; replace “Prediction Accuracy” wording with a regression-appropriate label (e.g. R² or simply drop the stat) once real evaluation numbers exist; until then mark the block as illustrative rather than removing the polished hero layout.

!Player portal shows a “Power Hitter” style badge

Section 40/88 restrict raw archetype output to the Coach view. The badge in the current Player prototype reads like a literal K-Means archetype label shown directly to the player.

Resolution During Phase 9 conversion, confirm with the actual archetype logic whether this stays as a general “playing style” descriptor (acceptable, Coach-approved, static profile tag) or must be removed until a Coach explicitly shares it. Default: keep it as a profile-level “playing style” tag distinct from the live AI_Predictions.player_archetype field, not wired to the ML pipeline directly.

!No training / coach-evaluation dataset supplied

Only players.xlsx and match_performance.xlsx were provided. FR4, the Training Recommendation Module and part of the ML feature set (attendance, drills, fitness, coach rating) have no source data.

Resolution Generate a proposal-aligned synthetic Training_Records dataset in Phase 11, clearly labelled SYNTHETIC PROTOTYPE DATA — FOR ACADEMIC DEVELOPMENT / TESTING, using the exact field names/scales already validated in the Coach prototype (attendance %, drill completion %, batting/bowling/fielding/fitness scores 0–100, coach rating 1–10).

!Demo identity mismatch between UI mockups and real dataset

The HTML prototypes use P001 = “Kasun Perera” and Coach “Ravi Jayasinghe” as placeholder demo identities. The actual players.xlsx has P001 = “Veer Rao” (Bowler), a different person entirely.

Resolution Per the brief's own rule (“preserve demo identities unless the actual files show a newer agreed identity”), the real dataset wins: MySQL is seeded from players.xlsx / match_performance.xlsx as-is, and the hardcoded “Kasun Perera” text in the prototypes is replaced by real seeded data during API integration (Phase 9) — exactly the general rule in section 90 about removing hardcoded prototype data.

Optional / judgement call
~Coach “Dev Plans” merges Development Plan + Goal Tracking into one page

Acceptable simplification. The proposal's own Table 13 groups Coach pages loosely; a single page with two tabs (Plans / Goals) avoids an unnecessary extra page while both database entities (Development_Plans, Player_Goals) stay distinct underneath.

~Match dataset carries extra fields beyond the proposal's minimum example list

fours, sixes, maidens, dot_balls, wides, no_balls, misfields all exist in match_performance.xlsx / the Match Entry prototype. Section 28 explicitly allows keeping useful existing fields — retained as-is, none are mandatory ML inputs.

~players.xlsx player_status has three values, not two

Active / Inactive / Left Academy, rather than a strict Active/Inactive binary. Recommendation: keep all three as a documented status enum (still simple, and already consistent throughout the real dataset) rather than collapsing “Left Academy” into “Inactive” and losing information.

~Player age vs. U19 eligibility must be evaluated per match date, not “today”

Because match history spans 2023–2025, several players are already over 19 by August 2026. This is expected for historical academy data (players graduate out) and is not a data quality problem — feature engineering and eligibility checks should reference the relevant match/season date, never the current system date.

Live prediction flow (FR11 / FR20)

1. Coach selects a Player in the React Coach Portal

↓

2. FastAPI retrieves that player's match, training and rating history from MySQL

↓

3. AI/ML service builds features → loads preprocessor.joblib → loads performance_model.joblib → predicts

↓

4. Performance Potential Score (0–100) → Potential Level (Low/Medium/High) → K-Means archetype

↓

5. Training Recommendation Module scores training focus areas (weighted logic)

↓

6. Saved to AI_Predictions (status = PENDING) and returned to the Coach

↓

7. Coach reviews → Accept / Reject / Modify → status updated → optional Goal / Plan / Feedback created

model.fit() never runs on this path — training happens separately, offline, in the ML notebook (Section O below).

Target definition (Section 65)

What the Performance Potential Score (0–100) represents: a composite estimate of a player's near-term match-performance trajectory, built from historical batting/bowling/fielding/training/coach-rating data — not a measured ground truth, since no such number exists in real cricket.

How the training target will be constructed: from each player's later chronological matches/training (e.g. a forward-looking contribution/consistency score), never from the same-row inputs used as features, and documented as a formula in the ML notebook so it is fully defendable.

When it is predicted: at the point the Coach requests a prediction, using only data available up to that point in the player's history — matches with a chronological train/test split, recent-form features built with backward-looking rolling windows (shifted before the target row) to prevent leakage.

Feature sources (excludes Section 64's disallowed shortcuts)

GroupCandidate features
BattingRecent runs, strike rate, batting average, boundary %, recent-form index
BowlingRecent wickets, economy, dot-ball %, bowling consistency
FieldingCatches, run-outs, fielding score
TrainingAttendance %, drill completion %, fitness score
Coach evaluationCoach rating (numeric)
Engineeredconsistency_score, overall_contribution_score (formulas documented in the notebook, Section 63)
Explicitly excludedplayer_id, player_name, height_cm, weight_kg, and any same-row future/target-match statistic

Player Archetype Clustering (FR12)

K-Means on scaled, aggregated per-player features (StandardScaler); K chosen by testing a sensible range and comparing Silhouette Scores; cluster centroids inspected before any label is assigned. Only archetypes the discovered clusters actually support get used — the proposal's example list (Power Hitter, Anchor Batter, Bowling Specialist, Death Bowler, All-Rounder Candidate, Fielding Specialist) is a menu, not a quota.

Training Recommendation Module (FR13) — not a third model

Default weighting (proposal's own example, centrally configured and adjustable after testing):

Prediction result30%Recent form20%
Attendance15%Weakness score15%
Fitness score10%Coach rating10%

Output is always explainable (focus area + reason + priority), and the Coach can Accept / Reject / Modify — stored via recommendation_status, original_recommendation, modified_recommendation on AI_Predictions (Section 80: no separate table needed).

Performance Drop Alert (FR14) — rule-based, not ML

Compares each player's recent window (e.g. last 3–5 matches/sessions) against their own historical average for batting contribution, economy, attendance and fitness. A meaningful negative deviation produces an alert (Player, Area, Reason, Severity, Date) surfaced only on the Coach Dashboard. No model, no training, no persistence table required beyond what Match_Performance/Training_Records already hold.

Persistence & retraining policy

Saved artifacts in ai_service/saved_models/: performance_model.joblib, preprocessor.joblib, kmeans_model.joblib, kmeans_scaler.joblib. Training happens once, offline, in the Jupyter notebook — the live app only ever loads and predicts. Retraining is manual/periodic (after a tournament, monthly, or quarterly), never continuous or triggered by a Coach action, matching Section 72.

Software testing layers

  • Regression (primary): MAE, RMSE, R², compared against a simple baseline
  • Classification (secondary, optional): Accuracy, Precision, Recall, F1, confusion matrix
  • Clustering: Silhouette Score + qualitative Coach review of cluster meaningfulness
  • Recommendation module: explanation clarity + usefulness, via the UAT instrument (no fabricated Coach feedback)
  • System success: dashboard/response time, task completion, manual-effort reduction — measured where real usage exists, otherwise the measurement method is prepared
